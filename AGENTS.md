# AGENTS.md

> **Purpose.** Written for an **AI agent working in a local clone** of this repository: editing a pattern, adding one, validating a change, or deploying a pattern to test it. For VPC Lattice knowledge, load [`SKILLS.md`](SKILLS.md). For a human introduction, start with [`README.md`](README.md).

## Find your way around

[`llms.txt`](llms.txt) is the index: every category, pattern and reference page, each with the question it answers and the IaC it ships. Read it before listing directories or searching.

| Directory | Contains |
|-----------|----------|
| [`patterns/1-simple_architectures/`](patterns/1-simple_architectures/) | Single-account fundamentals, one pattern per target type (EC2, Auto Scaling group, Lambda, ECS, EKS) plus RDS as a VPC resource |
| [`patterns/2-multi_account/`](patterns/2-multi_account/) | Cross-account sharing with AWS RAM, in the centralized and distributed models |
| [`patterns/3-advanced_architectures/`](patterns/3-advanced_architectures/) | Designs beyond basic consumer-provider connectivity |
| [`patterns/4-auth_policies/`](patterns/4-auth_policies/) | A reference toolkit, not a deployable pattern: auth policy snippets (`policies/`) and SigV4/SigV4A signing (`signing/`) |
| [`patterns/5-agentic_architectures/`](patterns/5-agentic_architectures/) | AI agents connecting to MCP servers, REST APIs, other agents and models: VPC Lattice for the connectivity and agent-level access, an optional AI gateway (self-hosted or Amazon Bedrock AgentCore Gateway) for per-tool controls, and AWS Agent Registry for discovery. The agent, tool and gateway code all its patterns build is shared in `applications/` |
| [`patterns/tf_modules/`](patterns/tf_modules/) | Shared Terraform modules, the only shared-module root |

Each deployable pattern has a `README.md` (architecture, testing, cleanup), a `terraform/` and a `cloudformation/` directory, laid out as in [Directory layout](CONVENTIONS.md#2-directory-layout). Patterns are building blocks: a real design often composes several, so start from the closest one rather than looking for a directory per use case.

## Rules that are easy to break

[`CONVENTIONS.md`](CONVENTIONS.md) is the authoritative contract. These are the rules a change most often breaks:

- **Never hand-edit `terraform/README.md`.** It is generated by terraform-docs from `.header.md` and the module's inputs and outputs; edit `.header.md` and regenerate with `.config/.terraform-docs.yaml`.
- **Keep CloudFormation and Terraform in parity.** EKS is the only Terraform-only pattern; `patterns/4-auth_policies/` has no IaC.
- **Changing `patterns/5-agentic_architectures/applications/` changes every agentic pattern.** Select pattern-specific behaviour through configuration (the connectivity mode, or a registry record's fields), and check that the other patterns keep their code path.
- **Take version pins from [Version pins](CONVENTIONS.md#3-version-pins)**, including the pattern-specific floors. Do not write them from memory.
- **Keep the secure defaults**: IMDSv2, encrypted EBS root volumes, HTTPS listeners, the RDS managed master password, access logging on by default, and `AWS_IAM` with an open auth policy on service-exposing patterns. Every Checkov suppression carries a justification.
- **Keep the indexes in sync in the same change.** Adding, removing or renaming a pattern updates the catalogs listed in [Catalog and agent-index synchronization](CONVENTIONS.md#9-catalog-and-agent-index-synchronization). A pattern missing from `llms.txt` is a bug.
- **Treat file paths as a public interface.** `llms.txt`, the `README.md` anchors `#why-vpc-lattice` and `#key-concepts`, and the category and pattern READMEs are linked by path from outside this repository, including the Amazon VPC Lattice agent skill. Do not rename or move them without calling it out in the pull request.
- **Put the MIT-0 license header on every new IaC source file**, and follow the [naming scheme](CONVENTIONS.md#1-naming-scheme).
- **Do not hard-wrap human-facing markdown.** One paragraph is one line.
- **Never invent a VPC Lattice property.** Confirm it against the [Amazon VPC Lattice User Guide](https://docs.aws.amazon.com/vpc-lattice/latest/ug/what-is-vpc-lattice.html) before writing it in a pattern or page.

## Validate a change

Every check is static: none needs AWS credentials or creates a resource. Run the ones that match what you changed, and say in your hand-back which ran and which did not.

| You changed | Run |
|-------------|-----|
| Terraform | `terraform fmt`, `terraform validate`, `tflint`, `terraform-docs` — through pre-commit |
| CloudFormation | `cfn-lint` — through pre-commit |
| Terraform or CloudFormation | `checkov` — through pre-commit |
| Any markdown file, or `llms.txt` | `lychee --no-progress --max-retries 2 --accept 200,206,429 <files>` |
| `skills/` | `python3 skills/vpc-lattice-blueprints/scripts/validate-package.py` |
| Anything, before opening a pull request | `pre-commit run --all-files` |

The tool versions and install steps are in [Local checks (pre-commit)](CONTRIBUTING.md#local-checks-pre-commit). If a tool is not installed, say so rather than reporting the check as passed.

Follow [`CONTRIBUTING.md`](CONTRIBUTING.md): work on a branch of a fork, open an issue first for significant work, and fill in the [pull request template](.github/pull_request_template.md) — its checklist mirrors the rules above for each area a change touches.

## Deploy a pattern to test a change

- **Ask before deploying.** Every pattern creates billable resources in the user's account. Read the pattern README's cost note first, recommend a non-production account, and run the README's cleanup steps when finished.
- **Use the pattern's own tooling.** Terraform: `terraform init`, `plan`, `apply`, then `destroy`; multi-account patterns deploy per account and tear down in reverse order. CloudFormation: the pattern's `Makefile` (`make deploy` / `make undeploy`), which pins a Region — edit it to deploy elsewhere.
- **Test with the README's steps.** A service resolves to a `169.254.171.x` address and a VPC resource to a `129.224.0.x` address; Network Segment Access is the exception and reaches the provider's real IP addresses. The Agentic Architectures patterns build container images first (`./deploy.sh` in Terraform, `make deploy` in CloudFormation) and are tested by chatting with each agent (`./chat.sh ecs|runtime` or `make chat AGENT=ecs|runtime`).
- **Ask about access control.** Service-exposing patterns ship an open auth policy; if the user wants to restrict access, apply a policy from [`patterns/4-auth_policies/policies/`](patterns/4-auth_policies/policies/).
- **When a request fails**, follow [How do I troubleshoot VPC Lattice connectivity?](README.md#how-do-i-troubleshoot-vpc-lattice-connectivity) and read the pattern's access logs.
