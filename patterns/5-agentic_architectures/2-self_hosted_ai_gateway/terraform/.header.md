# Amazon VPC Lattice - Self-Hosted AI Gateway (Terraform)

Terraform implementation of the Self-Hosted AI Gateway pattern (LiteLLM). For the architecture, what gets deployed, and the connectivity testing steps, see the [pattern README](../README.md).

| File | Resources |
|------|-----------|
| `main.tf` | Common items: Amazon ECR repositories, Amazon ECS cluster, IAM roles |
| `central.tf` | The `agents` and `backends` service networks and their access logging; endpoints VPC, interface VPC endpoints, resource gateway and one single resource configuration per endpoint (associated with the networks that use it); private hosted zones for the services' custom domain names (`ai-gateway` for the VPCs that call it, the backends for the gateway VPC) |
| `gateway.tf` | The gateway VPC (VPC association to `backends`), the AI gateway (LiteLLM on Amazon ECS), its database (Amazon RDS for PostgreSQL), the deploy-time secrets and the `ai-gateway` service with its auth policy |
| `agent_registry.tf` | AWS Agent Registry and its records (the gateway's MCP, A2A and model endpoints) |
| `consumer.tf` | Consumer VPC A (VPC association) with the self-hosted agent on Amazon ECS, and consumer VPC B (service network endpoint) with the agent on AgentCore Runtime |
| `backends.tf` | The backends, each published as a VPC Lattice service in `backends` with its custom domain name and auth policy: the MCP server and the REST API (AWS Lambda), and the triage A2A agent (Amazon ECS) in the provider VPC |
| `deploy.sh` / `chat.sh` | Deployment in three steps (images first), and the chat client for the [tests](../README.md#testing-connectivity) |

## Prerequisites

- **AWS Account**: With appropriate IAM permissions, and Amazon Bedrock model access for `model_id`
- **Terraform**: >= 1.3.0 installed
- **AWS CLI**: Configured with credentials, with the Session Manager plugin (for ECS Exec in the tests)
- **Docker**: With `buildx`, to build `linux/arm64` images
- **Custom domain and certificate**: a domain for the services (`hosted_zone_name`) and an ACM certificate that covers `*.<hosted_zone_name>` (`certificate_arn`), in the account and Region you deploy to
- **Permissions required**:
  - VPC Lattice: Service networks, services, target groups, resource gateways, resource configurations
  - EC2: VPC, subnets, security groups, VPC endpoints
  - Route 53: private hosted zones and records
  - ECS, ECR, Lambda, IAM, CloudWatch Logs
  - Amazon RDS, AWS Secrets Manager
  - Amazon Bedrock AgentCore (Runtime) and AWS Agent Registry

## Deployment

```bash
# Clone the repository
git clone https://github.com/aws-samples/amazon-vpc-lattice-blueprints.git

# Navigate to the Terraform directory
cd patterns/5-agentic_architectures/2-self_hosted_ai_gateway/terraform

# Configure variables in terraform.tfvars: hosted_zone_name and certificate_arn (required); identifier, aws_region, model_id (optional)

# Deploy: ECR repositories, then the ARM64 images, then the rest of the pattern and the registry record submission
./deploy.sh
```

The script runs three steps: it creates the Amazon ECR repositories, builds and pushes the agent, triage and LiteLLM gateway images (`linux/arm64`), and deploys the rest of the pattern. It then submits the AWS Agent Registry records, which the registry approves automatically.

## Testing

Run the [Testing Connectivity](../README.md#testing-connectivity) steps by chatting with each agent:

```bash
./chat.sh ecs       # agent-ecs, through ECS Exec
./chat.sh runtime   # agent-runtime, through InvokeAgentRuntime
```

## Cleanup

```bash
terraform destroy
```

> **Note**: AgentCore Runtime ENIs can remain in consumer VPC B for some hours after the agent is deleted (see [AgentCore Runtime VPC](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-vpc.html)). If `terraform destroy` fails on that VPC, run it again later. The access-logging log groups are managed by this pattern and are removed with it.

## Observability: Access logging

Each service network logs to its own `/aws/vpclattice/<network>-<identifier>` group (7-day retention): the `agents` group records the hop to the gateway, and the `backends` group records the gateway's hop to the backends. The `SERVICE` log type records every request to the VPC Lattice services (caller principal, auth decision, path and status code), and the `RESOURCE` log type records the connections to the central endpoints. LiteLLM's own logs add the virtual key, model and cost of each request.

> **Cost note**: This pattern runs an Amazon RDS for PostgreSQL instance and Amazon ECS Fargate tasks while deployed, and access logging uses CloudWatch Logs vended-logs pricing (ingestion + storage).
